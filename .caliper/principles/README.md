# H-OS Principles — How This Works

These files are the parent principles of the **H-OS** project (HiraTechLabs).
Every app inside H-OS (H-HR, H-Asset, H-Finance, ...) inherits them and may add its own.
Caliper's Planning, Execution and Review models are bound by them.

H-OS is an integrated business operating system: modular monolith by default, app ownership boundaries enforced, and cross-app communication through published contracts and versioned events. The backend stack choice is **under re-evaluation**: `DEC-0001` (NestJS) is `proposed` and `DEC-0008` compares Go, C# + ASP.NET Core, Java + Spring Boot and the NestJS baseline; no replacement is approved. The design system and dashboard rules remain subject to approved Decisions before additional visualization libraries are introduced.

Arabic overview for humans: `README.ar.md`.

## Layers

| Layer | File | Read by models |
|---|---|---|
| Digest | `CORE.md` | Always (short, ~1 page) |
| Domain files | `tech-stack.md`, `clean-architecture.md`, `clean-code.md`, `security.md`, `business.md`, `test.md`, `logs.md`, `performance.md`, `ui-ux.md`, `git.md`, `decisions.md`, `graph.md` | Only the rules the resolver selects |
| App deltas | `apps/<app>/.caliper/principles/*.md` | Same format; only additions and tightenings |
| Index | `INDEX.generated.json` | Generated by Caliper; never edited by hand |

Models do NOT read whole domain files. They read `CORE.md`, then the **Task Brief** that Planning builds from the resolver output.

## Rule format (machine-parsable)

Every rule is one block:

```
### SEC-001 [must|arch-test] api, auth
Rule statement in one or two sentences.
Why: optional, only when not obvious.
```

The resolver ignores `README*.md` and anything inside fenced code blocks.

Heading grammar: `### <ID> [<level>|<enforce>] <tags comma-separated>`

- **ID**: `<DOMAIN>-<NNN>`. App rules are prefixed with the app code, e.g. `HR-BIZ-001`. IDs are never reused.
- **level**: `must` (violation blocks merge) or `should` (violation needs a written reason in the PR).
- **enforce**: how the rule is checked. One of:
  - `lint`: static analysis / formatter / type checker
  - `arch-test`: dependency-cruiser or architecture tests
  - `test`: an automated test that must exist
  - `ci`: a CI gate or scan
  - `review`: only the Review model and the human can check it (weakest; minimize these)
- **tags**: from the fixed vocabulary below. Tag `*` means the rule applies to every task.

## Tag vocabulary

`*` `api` `db` `migration` `domain` `events` `auth` `permissions` `org-tree` `money` `audit` `files` `jobs` `config` `deps` `logging` `testing` `git` `perf` `ui` `i18n` `a11y` `docs` `graph` `decision` `ai` `infra`

New tags require a Decision.

## Inheritance

1. Effective rule set of an app = all H-OS rules + the app's own rules.
2. An app may **add** rules (own prefix).
3. An app may **tighten** a parent rule: restate it with `overrides: <ID>` on the line after the heading, with stricter text.
4. An app may **relax** a parent rule only with `relaxes: <ID>` plus `decision: DEC-NNNN` pointing to an accepted Decision that has a review date. Otherwise the resolver fails.
5. Principles change only through a Decision (see `decisions.md`).

## Resolver contract (Caliper implements)

```
caliper principles resolve --project <app> --tags <t1,t2> [--task-type feature|bugfix|refactor|chore]
```

Output (the Task Brief section "Applicable rules"):
1. All rules tagged `*` (the CORE rules).
2. All `must` rules whose tags intersect the requested tags.
3. All `should` rules whose tags intersect the requested tags.
4. Accepted Decisions whose `affects` paths or tags intersect the task.
5. Graph neighbors of the modules the task touches (see `graph.md`).

Planning chooses the tags from the request. Execution receives only this brief. Review receives the diff plus the same brief and answers per rule ID (`SEC-001: pass|fail|n/a`). CI enforces everything marked `lint`, `arch-test`, `test` and `ci` regardless of what any model read.

## Metrics Caliper should report

- Enforcement coverage: share of rules that are not `review`. Goal: increase over time.
- Rules with no tag intersection in the last N tasks (candidates for pruning).
- Violations caught by Review but not by CI (candidates to automate).

## Adding or changing a rule

Open a Decision, then edit. Keep rules atomic: one rule, one check. If a rule needs more than three sentences, split it.
